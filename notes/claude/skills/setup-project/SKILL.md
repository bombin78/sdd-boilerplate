Аргумент: $ARGUMENTS

Скилл из трёх частей: «Стек», «Читатель» и «Проект». Без аргумента
выполняются все, по порядку: темы для читателя и карта кода зависят
от стека. С аргументом «стек», «читатель» или «проект» — только эта
часть.

Вопросы задавай инструментом AskUserQuestion: до 4 вопросов за раз,
у вопроса от 2 до 4 вариантов, свой ответ пользователь пишет в «Other».
Ни одного файла не меняй до шага «Итог и запись».

## Часть 1. Стек

### 1.1. Определить стек по файлам

Прочитай, что есть в корне проекта:

- файлы зависимостей: `package.json`, `pyproject.toml`,
  `requirements.txt`, `go.mod`, `Cargo.toml`, `composer.json`, `Gemfile`;
- файлы настроек: `tsconfig.json`, `next.config.*`, `vite.config.*`,
  `nuxt.config.*`, `tailwind.config.*`, `postcss.config.*`,
  `components.json` (shadcn/ui), `prisma/schema.prisma`, `drizzle.config.*`,
  `docker-compose.yml`, `Dockerfile`, `.github/workflows/`;
- папки верхнего уровня, кроме `notes/`, `.claude/`, `.git/`,
  `node_modules/` и папок сборки.

Из них составь:

- технологии и версии. Версию бери из файла зависимостей или
  из установленного пакета, а не по памяти;
- команды проверки: lint, проверка типов, тесты, сборка. В
  `package.json` — раздел `scripts`. Раздели их на два списка раздела
  «Проверка» `stack-rules.md`: «Перед отчётом» — все команды,
  «После каждой правки» — быстрые. Что такое быстрые — в комментарии
  к разделу. Если не ясно, какие команды долгие, спроси пользователя.
  В маленьком проекте списки одинаковые. Если команда запускается через
  npm или npx, пиши `--no-update-notifier` сразу после `npm` или `npx`:
  `npm --no-update-notifier run lint`. После команд добавь абзац
  о флаге из комментария в разделе «Проверка» `stack-rules.md`.
  Перед этим прочитай `.claude/settings.local.json`: если в нём нет
  ключа `env` с `npm_config_update_notifier: "false"`, скажи
  пользователю, что его нужно добавить по разделу про этот файл
  в `notes/README.md`. Для pnpm, yarn и bun это правило не действует:
  проверено только для npm;
- папки с кодом для шаблонов путей;
- документацию в проекте: папки `docs/` внутри установленных пакетов,
  например `node_modules/next/dist/docs/`.

Покажи пользователю найденное одним списком и спроси, всё ли верно.
Исправления пользователя важнее того, что найдено в файлах.

Если `stack-rules.md` уже заполнен, сравни найденное с записанным
и спрашивай только о различиях: новая библиотека, другая версия,
пропавшая команда. Раздел «Код» при повторном запуске не меняй.

### 1.2. Пустой проект: спросить о технологиях

Если файлов зависимостей нет, проект пустой. Тогда спроси по очереди,
каждый раз с вариантами и с «Other»:

1. Что это за проект: сайт с интерфейсом, API без интерфейса,
   программа для командной строки, библиотека.
2. Язык: TypeScript, JavaScript, Python, Go или другой.
3. Фреймворк. Варианты подбери под ответы 1 и 2: например, для сайта
   на TypeScript — Next.js, Nuxt, SvelteKit, Vite с React.
4. Стили и компоненты, если есть интерфейс: Tailwind, CSS-модули,
   shadcn/ui, другая библиотека компонентов или без неё.
5. Данные: база данных и как с ней работать — PostgreSQL, SQLite,
   MongoDB, без базы; Prisma, Drizzle, SQL без ORM.
6. Вход пользователей: Auth.js, своя реализация, сервис, без входа.
7. Тесты: Vitest, Jest, Playwright, pytest, пока без тестов.
8. Запуск и выкладка: Docker, сервер, хостинг, пока не решено.
9. Менеджер пакетов, если язык его предполагает: npm, pnpm, yarn, bun.

Ответ «пока не решено» — нормальный ответ. В `stack-rules.md` такой
пункт записывается как «не выбрано», и при следующем запуске
`/setup-project стек` вопрос задаётся снова.

Команды проверки для пустого проекта предложи по выбранному стеку,
одинаковые в обоих списках раздела «Проверка», и отметь
в `stack-rules.md`: «предложено, проверить после установки».
Флаг `--no-update-notifier` добавляй по правилу из шага 1.1.
Шаблоны путей предложи по тем папкам, которые создаёт генератор
выбранного фреймворка.

### 1.3. Вопросы, которых нет в файлах

Даже если стек найден по файлам, спроси:

- если есть интерфейс — на каких ширинах экрана проверять вёрстку,
  в каких темах (светлая, тёмная);
- какие части кода не трогать без задачи: например, схему базы
  и серверную логику;
- для известного стека: добавить ли готовый набор правил в раздел
  «Код» и «Вёрстка». Готовые наборы — в комментариях `stack-rules.md`;
- ведутся ли задачи проекта в трекере: Jira, YouTrack, GitHub Issues
  или трекера нет. Ответ записывается в строку «Трекер задач»
  `notes/claude/common-rules.md`: название трекера или «нет». Если
  трекер есть, у каждой задачи будет номер в нём, и этот номер
  ставится в имя ветки.

## Часть 2. Читатель

Читатель — тот, кому Claude пишет ответы. Раздел «Читатель»
в `notes/claude/answer-rules.md` создаётся при каждом запуске заново:
старые списки не берутся за основу.

### 2.1. Составить темы

Темы — из двух источников:

- технологии из части 1. Крупную технологию дели на 2–4 темы по тому,
  что в ней встречается в работе. Например, Next.js: App Router
  (`page`, `layout`, адреса страниц); серверные компоненты
  и `"use client"`; Server Actions; кэширование.
- общие темы, которые встречаются в любом веб-проекте: HTTP
  (заголовки, коды статуса), cookies, рендеринг на сервере
  и в браузере, сессии и JWT, хеширование паролей, git, Docker,
  терминал Linux.

Если части 1 не было, прочитай технологии из раздела «Стек»
`stack-rules.md`. Если он не заполнен, сначала выполни часть 1.

### 2.2. Спросить

1. «Что из этого вы знаете уверенно?» — AskUserQuestion
   с `multiSelect: true`. До 4 вопросов за раз, по 4 темы в каждом,
   вопрос назван по группе тем.
2. «Что из оставшегося знаете частично: общее понятие есть, детали
   объяснять?» — так же, только по темам, которые не выбраны в шаге 1.
3. Всё, что не выбрано ни в шаге 1, ни в шаге 2, попадает в «Не знаю».
4. Один вопрос со свободным ответом: что уточнить по выбранным темам.
   Например, «TypeScript: пишу свои типы, дженерики знаю частично».

### 2.3. Владелец заметок

Спроси, какое имя ставить в имя ветки, например логин на GitHub.
Ответ записывается в строку «Владелец заметок»
`notes/claude/common-rules.md`. В проекте без трекера это имя стоит
в имени ветки вместо номера задачи из трекера. При передаче заметок
новый владелец запускает `/setup-project читатель`, и строка
заменяется его именем.

## Часть 3. Проект

`notes/project.md` — описание проекта: что делает продукт и как
устроен код. Claude читает его перед планом каждого этапа. Что пишется
в каждый раздел и примеры — в комментариях этого файла: прочитай их
перед работой.

Если части 1 не было, прочитай раздел «Стек» `stack-rules.md`. Если он
не заполнен, сначала выполни часть 1.

### 3.1. Проект с кодом

Если в части 1 стек найден по файлам (шаг 1.1), прочитай:

- README проекта, `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md`, папку
  `docs/` проекта — то, что из этого есть;
- дерево папок до второго уровня, кроме `notes/`, `.claude/`, `.git/`,
  `node_modules/` и папок сборки;
- точки входа: у веб-фреймворка — корневой layout и маршруты, у API —
  файл запуска сервера и регистрацию маршрутов, у программы —
  функцию `main`;
- схему базы: `prisma/schema.prisma`, миграции, модели ORM;
- список переменных окружения: `.env.example` или подобный. Сам `.env`
  не читай: в нём значения, в том числе пароли;
- настройки CI: `.github/workflows/`, `.gitlab-ci.yml` и подобные;
- папки и файлы тестов.

Если в проекте много кода, поручи чтение агенту Explore и возьми у него
только выводы. В монорепозитории карта строится по пакетам. Подробности
отдельных модулей не нужны: они добавляются по задачам.

Сценарии выбери по маршрутам и README, 3–5 главных. Каждый проследи
по коду от входа до базы или ответа. Если цепочку проследить
не удалось, сценарий записывается в раздел «Не проверено», а не
угадывается.

Потом спроси о том, чего из кода не понять:

- что делает продукт и для кого, если README этого не говорит;
- зачем нужны модули, назначение которых по коду не видно;
- какие части устарели или не используются.

### 3.2. Новый проект

Если проект пустой (шаг 1.2), спроси:

1. Что делает продукт — одной-двумя фразами.
2. Для кого он: кто пользователи.
3. Главные сценарии: что пользователь делает в продукте, 3–5 штук.
4. Чего в продукте не будет, хотя бы в первой версии.

Ответы на 3 и 4 — свободным текстом. Если генератор уже создал папки,
карта кода строится по ним, как в шаге 3.1. Если кода нет, разделы
«Карта кода», «Главные сценарии в коде», «Данные» и «Тесты и CI»
получают строку «пока нет: появится с этапами».

### 3.3. Повторный запуск

Если `notes/project.md` уже заполнен, найди коммиты после даты
в строке «Сверено с кодом»:

```bash
git log --oneline --since="<дата> 00:00" HEAD -- <папки из карты кода>
```

Время `00:00` обязательно: без него git пропускает коммиты того же
дня, сделанные раньше текущего времени суток.

Покажи, какие разделы могли устареть, и предлагай правки только для
них. Раздел «Что делает продукт» без ответа пользователя не меняй.

## Итог и запись

1. Покажи в чате, что запишешь:
   - `notes/claude/stack-rules.md` — разделы «Стек», «Документация»,
     «Проверка», «Вёрстка», а в разделе «Код» — только то, что
     пользователь выбрал в шаге 1.3;
   - шаблоны путей — одинаковые в начале `stack-rules.md`
     и `notes/claude/code-rules.md`;
   - раздел «Читатель» в `notes/claude/answer-rules.md` — три списка;
   - строки «Трекер задач» (шаг 1.3) и «Владелец заметок» (шаг 2.3)
     в `notes/claude/common-rules.md`;
   - `notes/project.md` — все разделы.
2. Запиши только после явного согласия пользователя.
3. В `stack-rules.md` и в двух строках `common-rules.md` замени
   «(заполняет /setup-project)».
   Комментарии `<!-- -->` с примерами оставь: они помогают при
   следующем запуске.
4. В `answer-rules.md` замени только три списка раздела «Читатель».
   Комментарий-болванку над ними удали. Остальные разделы файла
   не трогай.
5. В `project.md` замени `<имя проекта>` и «(заполняет
   /setup-project)», в строках «Дата» и «Сверено с кодом» поставь
   сегодняшнюю дату. Комментарии оставь.
6. Скажи пользователю, что `answer-rules.md` и `common-rules.md`
   загружаются при старте сессии: новые списки и строки подействуют
   после перезапуска Claude Code. `project.md` перезапуска не требует:
   Claude читает его перед планом этапа.
