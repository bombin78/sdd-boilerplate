# Задачи

Здесь лежат задачи по проекту: что сделать, как проверить и что уже
сделано.

## Папки

| Папка | Что в ней | Список задач |
|---|---|---|
| `app/` | всё внутри приложения: возможности, исправления, дизайн, тесты, переделка кода | [registry/app.md](registry/app.md) |
| `infra/` | всё, что запускает приложение и доставляет код до сайта: сервер, Docker, nginx, CI/CD, настройки GitHub, правила работы с ветками | [registry/infra.md](registry/infra.md) |
| `registry/` | списки задач всех направлений: по файлу на направление | — |

Папку выбирают по месту, где живёт изменение, а не по типу задачи.
Задача, в которой есть и логика, и дизайн, — одна задача в `app/`.

## Уровни

1. **Задача** — `NNNN-task`. Маленькая задача — файл `NNNN-task.md`.
   Задача из нескольких этапов — папка `NNNN-task/`: в ней
   `0000-description.md` и по файлу на каждый этап. Номер `0000` держит
   описание первым в списке файлов.
2. **Этап** — `NNNN-stage.md` внутри папки задачи. Этап — то, что
   принимается отдельно: одна ветка, один pull request. У маленькой
   задачи слоя этапов нет, она сама и есть один этап.
3. **Шаги** — разделы `## Шаг N. …` внутри файла этапа или маленькой
   задачи. Шаги пишутся, когда этап — инструкция, которую пользователь
   выполняет сам. Этап, который делает Claude, тоже можно разбить
   на шаги, если он большой: тогда у шага только что сделать, результат
   и отметка «Сделано», как в болванке `app/0001-task/0001-stage.md`. Маленький
   этап Claude пишется без шагов: что сделать и как проверить. У этапа,
   где код пишет пользователь, шаги — план кода: раздел «Как пользователь
   пишет код этапа».

Справочные заметки к этапу лежат рядом: `NNNN-stage-*.md`.

## Имена и номера

- Номера — четыре цифры: `0001`, `0002`… Так файлы сортируются по порядку
  до 9999.
- Нумерация своя в каждой папке: в `app/` и `infra/` — своя, этапы —
  своя в каждой задаче, шаги — своя в каждом этапе.
- Номер не меняется. Отменённая задача или этап остаётся в списке
  со статусом «отменён», новая получает следующий номер.
- Список задач направления — `registry/<направление>.md`: номер, порядок,
  задача, вид, статус. Новое направление — новая папка и новый файл
  в `registry/`.
- Порядок — в каком порядке задачи выполняются. Номер его не показывает:
  новая задача получает следующий номер, а место в очереди ей задаёт
  колонка «Порядок». Чтобы поменять очередь, меняют числа в этой
  колонке, номера задач не трогают.
- Статус задачи в `registry/` пишется так: «🟡 в работе с ГГГГ-ММ-ДД»,
  «🟡 в работе с ГГГГ-ММ-ДД, принят этап NNNN», «🟢 сделано
  ГГГГ-ММ-ДД». Значок заменяет цвет: в Markdown цвет текста не задать.
  Остальные статусы — без значка.
- В `0000-description.md` задачи из нескольких этапов —
  таблица этапов без статусов: статус этапа пишется только в начале
  файла этапа. У этапа без файла в таблице пишется, почему файла нет:
  «не расписан» или «отменён: …».

## Что в описании задачи или этапа

- цель: что не так сейчас и что должно получиться;
- чего не делать;
- раздел «Готово, когда» — в файле этапа и маленькой задачи: все
  условия приёмки одним пронумерованным списком. Каждое условие
  проверяется командой, в браузере или сверкой с источником. Отчёт
  идёт по номерам этих пунктов;
- статус;
- после приёмки — «Доработки по приёмке»: что пользователь попросил
  поправить и как исправлено.

## Требования и решения

Требования этапа — всё, что в файле этапа написано о результате:
абзацы шагов до отметки «Сделано», «Готово, когда», «Чего не делать».
Требования задачи — разделы описания задачи «Решения», «Что должно
получиться», «Чего не делать».

Решение — выбор, которого не было в требованиях. Оно приходит из трёх
мест: Claude выбирает по ходу шага и пишет в «Сделано», пользователь
отвечает на вопрос к плану — «Решения пользователя», пользователь
просит поправить при приёмке — «Доработки по приёмке».

Если решение меняет или уточняет требование, абзац с этим требованием
правится сразу, в той же правке. Запись о решении остаётся на своём
месте как история.

## Как Claude делает этап с приёмкой

Статус этапа меняется в начале файла этапа, у маленькой задачи —
в начале её файла. Статус задачи — в `registry/<направление>.md`.

1. Перед кодом показать в чате план: какие файлы и что в них меняется.
   Пользователь согласился с планом — статус этапа «в работе». Если
   этап первый в задаче — статус задачи в `registry/` «🟡 в работе
   с ГГГГ-ММ-ДД», дата — сегодняшняя.
2. Сделать правки. Если в этапе есть шаги, то в конце готового шага —
   строка «**Сделано ГГГГ-ММ-ДД.**» и что сделано, как у шага 1
   в болванке `app/0001-task/0001-stage.md`. Решение, принятое по ходу шага,
   правит требование — раздел «Требования и решения» выше.
3. Проверить и отчитаться, как сказано в разделе «После правок»
   `notes/claude/code-rules.md`, плюс каждый пункт раздела «Готово,
   когда» файла этапа. Перед отчётом — статус этапа «ждёт приёмки».
4. Ждать приёмки. Следующий этап начинать только после явного согласия
   пользователя («принято», «дальше» и подобное). После согласия —
   статус этапа «принят ГГГГ-ММ-ДД», статус задачи в `registry/` —
   «🟢 сделано ГГГГ-ММ-ДД», если этап последний, иначе «🟡 в работе
   с ГГГГ-ММ-ДД, принят этап NNNN» с прежней датой начала. Если
   пользователь просит доработать — статус этапа
   «в работе», дорабатывать текущий этап и снова проходить пункт 3.

Один этап — одна ветка от свежего `main` и один pull request.

## Как пользователь пишет код этапа

Код этапа пишет пользователь. Claude помогает составить план
и проверяет результат. В колонке «Вид» списка задач у такой задачи —
«код пишет пользователь». Файл этапа — по болванке
`app/0001-task/0001-stage.md`, статусы — те же, что у этапа Claude.

1. Claude читает код, который меняется, и вместе с пользователем
   составляет план: какие файлы меняются и что в каждом должно
   появиться. План записывается в файл этапа шагами `## Шаг N.`
   с «Что сделать» и «Результат». Готовый код Claude в план не пишет,
   если пользователь не попросил. Пользователь согласился с планом —
   статусы этапа и задачи меняются, как в пункте 1 раздела выше.
2. Пользователь пишет код по шагам. Claude в это время файлы кода
   не меняет и отвечает на вопросы, например через `/explain`.
   Отметку «**Сделано ГГГГ-ММ-ДД.**» в конце шага пишет пользователь
   или Claude по его просьбе.
3. Пользователь говорит, что код готов. Claude проверяет его:
   - запускает команды из раздела «Проверка»
     `notes/claude/stack-rules.md`;
   - сверяет код с каждым пунктом «Готово, когда», с правилами
     `notes/claude/code-rules.md` и `notes/claude/stack-rules.md`;
   - пишет отчёт: по каждому пункту «Готово, когда» — выполнен или нет
     и как проверен, дальше — замечания: файл, строка, что не так
     и как исправить.

   Код Claude сам не исправляет. Перед отчётом — статус этапа «ждёт
   приёмки».
4. Пользователь исправляет замечания и снова просит проверку, как
   в пункте 3. Замечание, которое пользователь решил не исправлять
   в этом этапе, Claude записывает в `backlog.md`. Приёмка и статусы
   после неё — как в пункте 4 раздела выше.

Ветка и pull request — как у этапа Claude.

## Имена веток

- Этап задачи: `<направление>/T<номер задачи>-S<номер этапа>`, например
  `app/T0001-S0002` — задача 0001 в `app/`, этап 0002.
- Маленькая задача без этапов: `<направление>/T<номер задачи>`,
  например `infra/T0003`.

Номера — те же четыре цифры, что в именах файлов. Ветку создаёт
пользователь.
