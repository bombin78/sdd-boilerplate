# Задачи

Здесь лежат задачи по проекту: что сделать, как проверить и что уже
сделано.

## Папки

| Папка | Что в ней | Список задач |
|---|---|---|
| `app/` | всё внутри приложения: возможности, исправления, дизайн, тесты, переделка кода | [registry/app.md](registry/app.md) |
| `infra/` | всё, что запускает приложение и доставляет код до сайта: сервер, Docker, nginx, CI/CD, настройки GitHub, правила работы с ветками | [registry/infra.md](registry/infra.md) |
| `registry/` | списки задач всех направлений: по файлу на направление | — |

Папку выбирают по месту, где живёт изменение, а не по типу задачи.
Задача, в которой есть и логика, и дизайн, — одна задача в `app/`.

## Уровни

1. **Задача** — `NNNN-task`. Маленькая задача — файл `NNNN-task.md`.
   Задача из нескольких этапов — папка `NNNN-task/`: в ней
   `0000-description.md` и по файлу на каждый этап. Номер `0000` держит
   описание первым в списке файлов.
2. **Этап** — `NNNN-stage.md` внутри папки задачи. Этап — то, что
   принимается отдельно: одна ветка, один pull request. У маленькой
   задачи слоя этапов нет, она сама и есть один этап.
3. **Шаги** — разделы `## Шаг N. …` внутри файла этапа или маленькой
   задачи. Шаги пишутся, когда этап — инструкция, которую пользователь
   выполняет сам: [instruction-mode.md](instruction-mode.md).
   Этап, который делает Claude, тоже можно разбить
   на шаги, если он большой: тогда у шага только что сделать, результат
   и отметка «Сделано», как в болванке `app/0001-task/0001-stage.md`. Маленький
   этап Claude пишется без шагов: что сделать и как проверить.

Справочные заметки к этапу лежат рядом: `NNNN-stage-*.md`.

## Имена и номера

- Номера — четыре цифры: `0001`, `0002`… Так файлы сортируются по порядку
  до 9999.
- Нумерация своя в каждой папке: в `app/` и `infra/` — своя, этапы —
  своя в каждой задаче, шаги — своя в каждом этапе.
- Номер не меняется. Отменённая задача или этап остаётся в списке
  со статусом «отменён», новая получает следующий номер.
- Список задач направления — `registry/<направление>.md`: номер, номер
  в трекере, порядок, задача, вид, статус. Колонка «Трекер» есть только
  в проекте с трекером. Новое направление — новая папка и новый файл
  в `registry/`.
- Порядок — в каком порядке задачи выполняются. Номер его не показывает:
  новая задача получает следующий номер, а место в очереди ей задаёт
  колонка «Порядок». Чтобы поменять очередь, меняют числа в этой
  колонке, номера задач не трогают.
- Статус задачи в `registry/` пишется так: «🟡 в работе с ГГГГ-ММ-ДД»,
  «🟡 в работе с ГГГГ-ММ-ДД, принят этап NNNN», «🟢 сделано
  ГГГГ-ММ-ДД». Значок заменяет цвет: в Markdown цвет текста не задать.
  Остальные статусы — без значка.
- В `0000-description.md` задачи из нескольких этапов —
  таблица этапов без статусов: статус этапа пишется только в начале
  файла этапа. У этапа без файла в таблице пишется, почему файла нет:
  «не расписан» или «отменён: …».

## Что в описании задачи или этапа

- цель: что не так сейчас и что должно получиться. Устройство кода
  не пересказывается: на него — ссылка на раздел `notes/project.md`.
  Пересказ устареет, а `project.md` пополняется после каждого этапа;
- в проекте с трекером — номер задачи в трекере, строкой «Трекер:
  PROJ-123» в начале файла задачи;
- чего не делать;
- раздел «Готово, когда» — в файле этапа и маленькой задачи: все
  условия приёмки одним пронумерованным списком. Каждое условие
  проверяется автотестом, командой, в браузере или сверкой
  с источником. Если условие можно проверить автотестом, оно
  проверяется автотестом: раздел «Тесты» `notes/claude/code-rules.md`.
  Отчёт идёт по номерам этих пунктов;
- раздел «План» — в файле этапа и маленькой задачи: какие файлы и что
  в них меняется. Записывается, когда пользователь согласился
  с планом;
- статус;
- после приёмки — «Доработки по приёмке»: что пользователь попросил
  поправить и как исправлено;
- после ревью pull request — «Доработки по ревью»: что попросил
  поправить проверяющий и как исправлено.

## Требования и решения

Требования этапа — всё, что в файле этапа написано о результате:
абзацы шагов до отметки «Сделано», «Готово, когда», «Чего не делать».
Требования задачи — разделы описания задачи «Решения», «Что должно
получиться», «Чего не делать».

Решение — выбор, которого не было в требованиях. Оно приходит из
четырёх мест: Claude выбирает по ходу шага и пишет в «Сделано»,
пользователь отвечает на вопрос к плану — «Решения пользователя»,
пользователь просит поправить при приёмке — «Доработки по приёмке»,
проверяющий просит поправить на ревью — «Доработки по ревью».

Если решение меняет или уточняет требование, абзац с этим требованием
правится сразу, в той же правке. Запись о решении остаётся на своём
месте как история.

## Как появляется задача

Работа над этапом не начинается, пока пользователь не принял файл
задачи и файл этапа. Это первая приёмка: приёмка спецификации до кода.

1. Задача приходит из трекера, от пользователя или из пункта
   `notes/backlog.md`.
2. Claude читает `notes/project.md` и код, которого задача касается.
   Потом предлагает направление (`app/` или `infra/`) и вид задачи:
   маленькая или из нескольких этапов, делает Claude или инструкция
   по шагам. Решает пользователь.
3. Claude пишет черновик по болванке: маленькая задача — по
   `app/0002-task.md`, задача из нескольких этапов — `0000-description.md`
   по `app/0001-task/0000-description.md`, инструкция — по
   `infra/0001-task.md`. Номер — следующий свободный в папке
   направления.
4. Пользователь читает черновик и правит его сам или просит поправить.
   Черновик принят, когда пользователь явно согласился. Тогда Claude
   добавляет строку в `registry/<направление>.md` со статусом
   «не начата». До согласия строки в списке нет.
5. Файл этапа задачи из нескольких этапов пишется так же: черновик,
   правки, согласие. Первый — после приёмки описания задачи, каждый
   следующий — после приёмки предыдущего этапа.

## Как Claude делает этап с приёмкой

Статус этапа меняется в начале файла этапа, у маленькой задачи —
в начале её файла. Статус задачи — в `registry/<направление>.md`.

1. Прочитать `notes/project.md` и найти коммиты после даты в строке
   «Сверено с кодом»:
   `git log --oneline --since="<дата> 00:00" HEAD -- <папки из карты кода>`.
   Свои коммиты прошлых этапов пропустить: они уже учтены. Если другие
   коммиты меняли папки из карты, сказать, какие разделы могли
   устареть, и предложить их сверить. Сверять только с согласия
   пользователя.

   Потом перед кодом показать в чате план: какие файлы и что в них
   меняется. Пользователь согласился с планом — записать его в раздел
   «План» файла этапа и поставить статус этапа «в работе». Если
   этап первый в задаче — статус задачи в `registry/` «🟡 в работе
   с ГГГГ-ММ-ДД», дата — сегодняшняя.
2. Сделать правки. Если в этапе есть шаги, то в конце готового шага —
   строка «**Сделано ГГГГ-ММ-ДД.**» и что сделано, как у шага 1
   в болванке `app/0001-task/0001-stage.md`. Решение, принятое по ходу шага,
   правит требование — раздел «Требования и решения» выше.
3. Проверить и отчитаться, как сказано в разделе «После правок»
   `notes/claude/code-rules.md`, плюс каждый пункт раздела «Готово,
   когда» файла этапа. Если этап поменял то, что описано
   в `notes/project.md`, — модуль, сценарий, таблицу, внешний сервис,
   тесты, — в конце отчёта, перед строкой статуса, предложить правки
   этого файла. Перед отчётом — статус этапа «ждёт приёмки».
4. Ждать приёмки. Следующий этап начинать только после явного согласия
   пользователя («принято», «дальше» и подобное). После согласия —
   статус этапа «принят ГГГГ-ММ-ДД», статус задачи в `registry/` —
   «🟢 сделано ГГГГ-ММ-ДД», если этап последний, иначе «🟡 в работе
   с ГГГГ-ММ-ДД, принят этап NNNN» с прежней датой начала. Правки
   `notes/project.md` из отчёта внести, если пользователь их не
   отклонил, и поставить сегодняшнюю дату в строке «Сверено с кодом».
   Если пользователь просит доработать — статус этапа «в работе»,
   дорабатывать текущий этап и снова проходить пункт 3.

**Ревью pull request.** Если проверяющий pull request просит поправить
уже принятый этап, это доработка. Статус этапа — «в работе»,
замечания и как они исправлены — в раздел «Доработки по ревью» файла
этапа, дальше пункты 2–4. Если pull request никто не проверяет, этот
абзац не нужен.

Один этап — одна ветка и один pull request. Ветка создаётся от свежей
версии основной ветки проекта, обычно это `main`.
Исключение — передача этапа другому владельцу заметок, раздел «Имена
веток».

## Этап по инструкции

Если этап — инструкция по шагам, которую выполняет пользователь,
порядок работы и правила текста — в [instruction-mode.md](instruction-mode.md).
Такой этап отмечен в начале файла этапа строкой «Этап — инструкция
по шагам, выполняет пользователь», а в колонке «Вид» списка задач —
«инструкция по шагам».

## Имена веток

- Этап задачи: `<направление>/<метка>/T<номер задачи>-S<номер этапа>`,
  например `app/PROJ-123/T0001-S0002` — задача 0001 в `app/`, этап 0002.
- Маленькая задача без этапов: `<направление>/<метка>/T<номер задачи>`,
  например `infra/ivan-petrov/T0003`.

Номера — те же четыре цифры, что в именах файлов. Ветку создаёт
пользователь.

Метка зависит от строки «Трекер задач» в `notes/claude/common-rules.md`:

- проект ведётся с трекером — метка равна номеру задачи в трекере,
  например `PROJ-123`. Номер в трекере есть у каждой задачи. Если его
  нет в файле задачи, Claude спрашивает его, прежде чем предложить
  ветку;
- трекера нет — метка равна имени из строки «Владелец заметок» в том же
  файле.

Метка разводит ветки разных программистов. У каждого программиста свои
заметки и свои номера задач, и без метки их ветки `app/T0001-S0001`
совпали бы.

**Передача незаконченного этапа.** В проекте без трекера новый
владелец заметок создаёт ветку со своим именем от ветки прежнего
владельца:

```bash
git switch -c app/new-name/T0001-S0001 app/old-name/T0001-S0001
```

В строке «Ветка» файла этапа пишутся обе: «Ветка
`app/new-name/T0001-S0001` — продолжение `app/old-name/T0001-S0001`».
Так видно, где остановился прежний владелец. Pull request делается
из новой ветки. В проекте с трекером ветка не меняется: новый владелец
продолжает работу в той же ветке.
